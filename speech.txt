《AI Coding 反直觉的那些事》

大家好，我是来自R&D研发中心的pixelcao，通过参加IgniteX创新项目的经历，讲述 AI Coding 中反直觉的一些事情，我的分享比较特殊，需要大家点击群里的URL链接，在浏览器而不是腾讯会议屏幕上观看画面，谢谢，请大家打开群里发的链接，给大家30秒的时间我们正式开始。

从千禧年开始，自然语言处理，也就是NLP领域，经历了一场少年派的奇幻漂流，从默默无闻的小众领域，到破土而出一夜之间站上世界之巅。

自从人类发明计算机以来，一直试图实现两件事：让计算机开口说话，和让计算机听懂人类说的话。

乔布斯是一个善于制造演讲效果的人。我相信每个人都记得，2008年乔布斯发布第一代MacBook Air时从信封中掏出电脑那一刻的惊艳。

我们那梦开始的地方是1984年，乔布斯发布Macintosh，最惊艳的一刻，莫过于他让Macintosh自己说话，用颇为机械口味的发音说出了：Hello，I’m macintosh, it sure is great to get out of that bag。

自那以后，下一个问题就是让计算机听懂人类说话，让机器说话叫TTS，让机器理解人类说话则叫做语音识别。为了让机器区分人类发音中的同音词，最先登场的是语言学家，他们试图编写成千上万条语法规则来让计算机实现语音识别，但他们失败于根本无法穷举所有的语法规则。接下来，基于概率的隐马尔可夫模型登场了，模型不再依赖手写规则，而是采用无监督的方式实现了语音识别和中文分词。

2007年，划时代的Windows Vista登场，它不光奠定了现代Windows架构的基础，在没人注意的角落，它还搭载了李开复领头开发的语音助手。Vista的语音助手可以通过规则匹配的方法实现了“打开记事本”、“点击属性菜单”等在现代人看来堪称简陋的操作，然而这却是NLP走进民用系统的开端。

2010年，苹果将一个第三方开发者的应用买了下来，那年秋天iPhone 4S横空出世，Hey Siri 成为全体苹果用户重复最多的话。而Siri技术的基础则是意图识别和槽位提取，也就是先对一句话做分类，接着再提取其中的关键信息，从而执行特定操作。大家如果有开过国产新能源车的话，相信也肯定用过车机上的语音助手，它们和Siri共享同一套底层原理。

2013年，业界出现了Word2Vec方法。词向量诞生了，它让模型学会了“国王 - 男人 + 女人 = 皇后” 这样的逻辑。次年出现了seq2seq方法，天生就能完成翻译任务，这就是文本生成模型的雏形。

2017年，可能是NLP界被引用次数最多的论文：Attention Is All You Need诞生了。次年谷歌提出了BERT模型，它的参数量达到了0.3个Billion，初具上下文理解的能力。

2023年初，成立仅一年的公司推出了ChatGPT，黄仁勋称之为AI界的iPhone时刻。从此NLP领域开始一路狂飙，它不仅无情的击碎了无数中小研究组织实现大模型的可能性，更作为大脑的存在催生出 coding agent产品，将“编程”这件事变成了已经被解决了的问题。

可以说，vibe coding 为小到程序员编写代码、大到全人类生产新鲜事物，开启了新的时代——这是最好的时代，也是最坏的时代。这是最好的时代，因为在你动动手指，手指尖跳动的字节，那就是全人类5000年的实践经验。这是最坏的时代，因为需求总量不变的情况下，飞跃的生产效率必然带来大规模的企业裁员，人类社会必须要作出改变，来适应新的生产体系。

不好意思啊，讲到现在才开始正题，我们的第一个重点是，敏捷开发从现在开始，都不够敏捷了。传统的敏捷流程是，产品需求 → 开发实现 → 产品体验 → 开发返⼯ → 测试验收 → 开发返⼯。它的速度被不同角色的人与人之间的反馈卡死了，如今AI写代码的速度以分钟计，但PM排期、产品评审、技术评审、产品体验、测试验收、开发返工仍然按天运转，流程上每多一个交接，AI提速带来的红利就会被吃掉一大截。

在参加Nex这个项目的过程中，我们团队每个人都是Nex的深度用户，虽然产品经理本身就会提需求，但开发自身也会边用边提出需要做的新特性，不经过产品确认直接反馈给AI，做完之后再进行自我反馈，直到给产品看到完成度非常高的90%纯度的成品。我们的owner兼PM，更是直接使用Nex本身来制作每次评审时的Nex的汇报材料。也许这不是唯一正确的软件开发方式，但却是在vibe coding浪潮下催生出的全新的团队合作和生产方式，这种方式能做到多、快、好、省中的前三项——因为我们确实消耗了很多token（笑）。

我的第二个重点是，不要盲目使用rules、skills。很多人对 agent 不甚了解，盲⽬添加了⼀堆⾃⼰也不熟的 rules、skills、MCP，结果是AI响应变慢、不同的rules之间打架冲突、生成代码时不知道是哪条规则在生效。而我让AI处理现有工程时，会先让AI通读一遍代码，然后问它一两个比较有深度的问题，如果它答得很好，说明 AI 对代码的理解已经到位了，再让它开发新功能。不管在前AI时代，还是后AI时代，人都贵在明白自己要做什么、做一件事需要什么，用合适的工具做合适的事情很重要。借此机会，我们用简短的语言描述一下这些名词的本质：LLM是agent的大脑，唯一真正在“思考”的部份。Agent则是对LLM的调用循环，LLM接受提示词，调用Tools工具，将反馈喂回LLM并以此循环，这个循环也被叫做ReAct。Tools则是LLM通过SSE/事件协议回调到你代码里的函数，本质上是LLM能调用的回调函数。MCP和Tools类似，但是实现在外部进程里，可以通过Shell或RPC来调用。Rules和Skills都是最终会拼接到System Prompt里的一段文本，前者约束模型行为，后者引导模型做事。Harness这个词不是具体某个工具，而是一套使用AI的方法论。

我要分享的第三个点，是为什么聪明人用AI反而会更累。在这里我要提出一个简单的公式：产出 = 输出速度 x 时间。假设Agent的输出速度是固定的，那要拿到更多产出就只剩一条出路，让AI时刻保持忙碌。那要怎么让AI保持忙碌呢——把你要解决的问题，编程可以让AI闭环探索的问题。比如你要修一个bug，传统流程是改 bug → ⼈验证 → 没好 → 再改 → ⼈再验证，即便有AI加持，人来验证这一环节仍然构成最大的瓶颈。而闭环的姿势则是，构造单元测试或helper脚本，让AI自己复现问题、尝试修复并验证，从此形成一个ReAct循环，整个过程不需要人工介入，ReAct循环停下的那一刻，就是问题被解决的终点。那为什么聪明人用AI反而会更累呢？还记得刚才的公式吗，你现在能让一个AI忙碌起来了，在单线程模式下，你的产出已经最大化。但是，聪明人的第一反应是，我能不能让多个AI同时都忙起来？于是聪明人在解决问题的时候，已经在让另一个AI评估下一个需求，并且让其他AI交叉Review。此刻，你已经不是你，你是一个研发、一个产品、一个PM复合叠加在同一个人身上的存在。最终，聪明人会把自己困在AI的牢笼中，而其他人在一边喝茶、一边等AI帮他修复问题、然后再人工验证，反而会更加轻松愉快。

参加Nex之前，我自己只是一个Agent开发领域的局外人，但是那个时间节点下，整个公司也确实没有太多经验丰富的Agent开发可用。我要分享的第四点，就是即便有AI加持，也不要尝试一步到位、一步登天，因为人对新事物的认知，是在实践过程中不断深化的。Nex是一个基于浏览器的vibe coding产品，目标是生产游戏落地页和活动页面，用传统计算机的话说，它是一个B/S（Browser/Server）模型的应用程序，它的Agent在后台，而呈现在前端。最初设计Agent的时候，我们采用的是SSE+XML的文本流，来让Agent指挥前端的WebContainer写代码，Agent的指令通过方便流式传输和解析的XML嵌入到文本流里发给前端。后来我们发现这种做法只能实现Agent到前端的单向指令，而无法从前端主动发送消息给Agent，于是重构成了SSE+WebSocket模型，单独开辟一个WebSocket通道来承载Tools调用所需的数据通道，将LLM的文本流和Agent的控制流分离解耦，为后面实现大量Tools留下了充足的扩展空间。这说明，即便有AI加持，也没有一上来就完美的理想架构，我们要做每个阶段应该做的事情，并且用AI来加速从一个阶段走向下一个阶段的速度。

我要分享的第五点，是Nex项目开发Agent中的核心干货——如何让Agent用起来又快又爽。相信每个人第一次使用ChatGPT时，都被它那子弹头一般的打字机效果征服了。但是，当LLM成为水和电一样的核心需要时，当复杂任务伴随着越来越长的提示词让LLM的首个token输出速度变得越来越慢时，当你越是着急让Agent帮你解决问题时，Agent却好死不死的经常卡住，你不知道在第几秒的时候Agent才会苏醒过来输出信息。在Nex项目中我们引入了我们称之为Prechat和Postchat的机制，它在对话开始和结束前运行小模型，评估任务复杂度，决定主Agent的思考深度，对简单任务采用low来降低TTFT，对复杂任务采用high来保证完成质量。同时设计了一个状态条，来不断用打字机效果来告诉用户主Agent当前在做什么，在等待Agent响应的过程中，让用户知道自己在等待什么，给他一个期待。最终，还有一些零零星星的优化手段，包括提示词动态组装、Tools执行并行化等一系列手段，最终让Nex的Agent用起来像子弹头一样流畅。做这些事情不难，但知道要做这些事情并不容易，正如我第一点所陈述的，敏捷开发已经不再敏捷，Nex项目迭代和完善如此之快的原因，就是我们每个人既是产品、也是研发，我们知道自己要做什么，我们自己就是自己产品的核心用户，我们在将新的idea呈现给产品的时候，已经拥有成品90%的完成度了。

我本来还有第六点要讲，但是通过Nex这个案例，我想下面这个论点已经得到了论证：即，Cursor、ClaudeCode、CodeBuddy 并不是市场唯一需要的产品，通过构建垂直领域的优秀体验，是有差异化竞争的生存空间的。

我要讲的第七点，是如何用AI做自己原本不擅长的事情。在Nex的Agent开发上，需要关心后端的SSE/WebSocket/ReAct Loop，前端则需要关心状态机、流式渲染、动画、Web容器，交互细节。用户可能遇到各种各样的问题，比如文本重复展示、Tool调用一直转圈、Agent无法解决语法错误等，如果是古法编程时代，我需要每个问题挨个排查、构造和复现bug，然后尝试修复。还记得第三点聪明人是怎么用AI的吗——将问题变成AI可以闭环解决的。我引入了一键复制诊断日志功能，把整个SSE事件流、tool调用细节、prechat评估和postchat结论、LLM Provider的反馈、WebSocket的关键事件，一键浓缩成纯文本复制到剪贴板，当用户出问题的时候，直接复制诊断日志给我。我拿着诊断日志，可以一键甩给AI排查，AI自己定位、自己给出优化方案。而我，原本不是经验丰富的Agent开发，甚至我都不是前端开发，但通过引入诊断日志将问题排查的过程让AI闭环化，我可以做好自己原本不擅长的事情。

最后一点，是一个警示忠告，有AI代劳之后，更应该关注人自身的哪些能力。作为研发，从“写代码”这件事中解放出来之后，你更需要具备独立完成一件事情的能力。完整的做一件事包含很多环节：构思 → 创意 → ⽅案 → 设计 → 施⼯ → 验收，在每个环节，你都需要首先意识到“这里能用AI boost一下”。也就是说，人要知道自己要做什么、知道做这件事需要什么、知道接下来该做什么。而今天和昨天的唯一区别，就是有了AI。所谓“不着急，慢慢来，但一定要快”，大概就是这个道理吧。我的演讲完毕，谢谢大家！
